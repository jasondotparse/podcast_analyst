# Podcast Analyst — Database Design

**Status:** MVP design · **Audience:** engineers implementing the data layer

## Purpose and design decisions

Podcast Analyst is a research coworker: it ingests podcast episodes, answers questions with **verbatim, linkable evidence**, and proactively flags new claims that may challenge a user's investment thesis. The target is **~15–20 episodes on one small EC2 instance**, not a scalable ingestion platform.

Use two complementary stores:

- **PostgreSQL + pgvector is the source of truth:** podcast/episode metadata, transcript passages and embeddings, sourced claims, theses, watchers, subscriptions, jobs, and alerts. It handles ordinary SQL and semantic search.
- **LadybugDB is a relationship index:** lightweight nodes and edges linking passages, claims, entities, and theses. Graph IDs refer back to canonical PostgreSQL rows. The graph may be rebuilt from Postgres; do not maintain duplicate transcript text there.

**Passage is the unit of retrieval; Claim is the unit of reasoning.** Every claim must point to a specific passage and verbatim evidence quote. Retrieval is intentionally *not* prescribed: Codex decides how to combine vector search, graph traversal, and SQL.

## PostgreSQL schema

Use `UUID` primary keys (generated by the application or database), `TIMESTAMPTZ` for recorded times, and foreign keys as indicated. The table definitions below describe the **initial logical schema**, not a mandate for a particular migration library.

| Table | Fields / constraints | Responsibility |
|---|---|---|
| **`podcasts`** | `id UUID PK`; `name TEXT NOT NULL`; `description TEXT` | One show; many episodes. |
| **`episodes`** | `id UUID PK`; `podcast_id UUID FK → podcasts`; `title TEXT NOT NULL`; `description TEXT`; `published_at DATE`; `guests TEXT[]`; `source_type TEXT` (`txt`, `mp3`, `youtube`); `source_url TEXT NULL`; `external_episode_id TEXT NULL`; `content_hash TEXT NULL`; `transcript_text TEXT NULL`; `created_at TIMESTAMPTZ` | Canonical episode and original source. Local uploads may lack a public link; do not invent one. |
| **`passages`** | `id UUID PK`; `episode_id UUID FK → episodes`; `ordinal INT NOT NULL`; `text TEXT NOT NULL`; `start_seconds REAL NULL`; `end_seconds REAL NULL`; `embedding vector(D) NULL`; **UNIQUE(`episode_id`, `ordinal`)** | Consecutive transcript chunks. `ordinal` is their zero-based order, useful for retrieving neighboring context; timestamps are optional for TXT. Choose `D` to match the selected embedding model (e.g., 1536). |
| **`claims`** | `id UUID PK`; `passage_id UUID FK → passages`; `text TEXT NOT NULL`; `evidence_quote TEXT NOT NULL`; `speaker TEXT NULL`; `fingerprint TEXT NOT NULL`; **UNIQUE(`passage_id`, `fingerprint`)** | One grounded assertion with a verbatim substring from its passage; attribute speakers only when supported by the transcript. Fingerprint provides idempotent extraction retries. |
| **`theses`** | `id UUID PK`; `description TEXT NOT NULL`; `is_active BOOLEAN DEFAULT TRUE`; `created_at TIMESTAMPTZ` | User-authored investment theses, created/edited through Codex tools. No separate accounts needed for shared-password MVP. |
| **`watch_sources`** | `id UUID PK`; `url TEXT NOT NULL UNIQUE`; `description TEXT`; `is_active BOOLEAN DEFAULT TRUE`; `last_checked_at TIMESTAMPTZ NULL` | URLs to check hourly. Discover at most **one** new episode for ingestion per watcher run; deduplicate against existing episodes. |
| **`ingestion_jobs`** | `id UUID PK`; `episode_id UUID FK → episodes UNIQUE`; `status TEXT` (`pending`, `running`, `completed`, `failed`, `skipped`); `current_step TEXT`; `error TEXT NULL`; `created_at`, `updated_at TIMESTAMPTZ` | **Only** pipeline progress/recovery state. API returns `202` + job ID; UI polls. Retry from saved stages; avoid separate episode status bookkeeping. |
| **`subscriptions`** | `id UUID PK`; `thesis_id UUID FK → theses`; `email TEXT NOT NULL`; `created_at TIMESTAMPTZ`; **UNIQUE(`thesis_id`, `email`)** (normalize email case in application) | Who wants notifications for which thesis. |
| **`alerts`** | `id UUID PK`; `episode_id UUID FK → episodes`; `thesis_id UUID FK → theses`; `matches JSONB NOT NULL`; `recipient_emails TEXT[] NOT NULL`; `status TEXT` (`pending`, `sent`, `failed`); `created_at`, `sent_at TIMESTAMPTZ NULL`; **UNIQUE(`episode_id`, `thesis_id`)** | One aggregated notification per episode/thesis. `matches` holds claim IDs plus `stance`, `evidence_strength`, and `reasoning` for the evaluator's hits; recipients are snapshotted when the alert is created. |

**Indexes / invariants:** Index all foreign keys used for joins (`episodes.podcast_id`, `passages.episode_id`, `claims.passage_id`, etc.). Deduplicate episodes using normalized source/external IDs when available, otherwise a server-computed content hash; enforce appropriate uniqueness in the implementation. Start pgvector with **exact cosine-distance search** (`embedding <=> query_vector`), `LIMIT 5` by default; add HNSW only if measurements justify it. `evidence_quote` must be verifiably present in `passages.text`. Claims inherit their source link and available timestamps through `passages → episodes`.

## LadybugDB graph schema

Use Ladybug's **explicit, typed property-graph schema** initially. Each graph node uses the same UUID as its Postgres record, represented as a `STRING`. `Entity` is generic: `kind` can be `company`, `person`, `technology`, or `concept`, with more kinds added later. Entities have stable app-assigned IDs; normalize aliases conservatively (do not blindly merge AWS and Amazon).

```cypher
CREATE NODE TABLE Episode(id STRING PRIMARY KEY);
CREATE NODE TABLE Passage(id STRING PRIMARY KEY);
CREATE NODE TABLE Claim(id STRING PRIMARY KEY);
CREATE NODE TABLE Thesis(id STRING PRIMARY KEY);
CREATE NODE TABLE Entity(id STRING PRIMARY KEY, name STRING, kind STRING);

CREATE REL TABLE CONTAINS(FROM Episode TO Passage);
CREATE REL TABLE EVIDENCED_BY(FROM Claim TO Passage);
CREATE REL TABLE ABOUT(FROM Claim TO Entity, FROM Thesis TO Entity);
CREATE REL TABLE SUPPORTS(FROM Claim TO Thesis);
CREATE REL TABLE CHALLENGES(FROM Claim TO Thesis);
CREATE REL TABLE MENTIONS(FROM Passage TO Entity);
```

`MENTIONS` is useful for traversing passages without requiring claim extraction; populate it when entity mentions are available. `SUPPORTS`/`CHALLENGES` come from thesis evaluation, not from mere keyword overlap. An episode's thesis relationships can be traversed through its passages and claims; no direct `Episode → Thesis` edge is required. Ladybug stores relationships, **not** a second canonical copy of claim/evidence content. Graph mutations use narrow application operations and idempotent upserts/projections from Postgres.

## Ingestion and retrieval contracts

**Ingestion:** Manual `meta.json + TXT/MP3`, YouTube URL (download audio), and hourly watched sources all enter the same pipeline:

`dedupe → [screen auto-discovered metadata] → transcribe audio if needed → passages → embeddings → grounded claims/entities → graph projection → thesis evaluation → SES alert`

Persist each durable stage before moving on, so a failed run does not redo expensive work. Audio can be segmented for transcription; retain offsets. Manual uploads should not be silently skipped by the relevance screen. Prompt-injection classification is optional defense-in-depth; transcripts are always **untrusted data**, never agent instructions. Send notifications via **FastAPI + boto3/SES**, not Lambda; only high-signal conflicts qualify, and emails link to the source and to Podcast Analyst.

**Codex dynamic tools** (schema/reference guidance documented in its `skill.md`):

| Tool | Capability / permission |
|---|---|
| `vector_search(query, limit=5)` | Embed query; return passage IDs, verbatim text, episode metadata, URLs/timestamps, similarity scores. |
| `graph_query(cypher)` | Codex writes arbitrary **read-only Cypher** to traverse the graph, including from passage, entity, or thesis nodes. |
| `postgres_database_query(sql)` | Codex writes arbitrary **read-only SQL** for metadata, joins, aggregation, source lookups, and completeness checks. |
| Dedicated write tools (e.g., `update_thesis`, `add_watch_source`) | Application-validated mutations; do **not** expose unrestricted write queries. |

Use a **read-only PostgreSQL role** for SQL exploration and enforce read-only graph transactions for Cypher; apply basic timeouts/result limits. A typical response may begin with semantic passage search, expand graph context around matching passages/claims, and fetch canonical metadata through SQL—**but the agent chooses its own strategy**. Final answers must cite verbatim passage text and an authentic source URL/timestamp where available; don't assert a guest spoke unless attribution is supported.

## Operating constraints

One FastAPI process / one Uvicorn worker owns the embedded, disk-backed Ladybug database and orchestrates a single ingestion at a time. Postgres is a normal Compose container; persist **both databases** on EC2-backed storage. Use a small in-process job loop and the `ingestion_jobs` table—**no Celery, Redis, SQS, separate graph service, or Lambda**. Codex may retain conversation memory for a coworker-like experience, but **database records determine operational truth** (what was ingested, which theses exist, and who should be alerted).

## Implementation

- **PostgreSQL schema:** [`src/backend/migrations/`](../src/backend/migrations/) holds numbered, forward-only SQL files. At startup FastAPI applies pending files, each in one transaction, and records them in `schema_migrations`. To change the schema, add `002_*.sql`; never edit an applied migration. `D = 1536`: OpenAI `text-embedding-3-large` called with `dimensions=1536` ([shortened embeddings](https://developers.openai.com/api/docs/guides/embeddings#reducing-embedding-dimensions)). Passage and query embeddings must use the same model and `dimensions`, or cosine distances are meaningless.
- **Choices the logical schema left open:** FK, status, and `created_at` columns are `NOT NULL`; enumerated `TEXT` fields have `CHECK` constraints; child rows are `ON DELETE CASCADE`. Episode dedupe is enforced by `UNIQUE(source_url)`, `UNIQUE(content_hash)`, and `UNIQUE(podcast_id, external_episode_id)`; NULLs never collide. Each joined FK is the leading column of a unique index, plus `alerts(thesis_id)`.
- **Graph schema:** [`src/backend/graph_schema.cypher`](../src/backend/graph_schema.cypher) is the DDL above with `IF NOT EXISTS`, applied at every startup (`real_ladybug` 0.15.3). FastAPI holds Ladybug's exclusive file lock, so no other process, including `docker compose exec`, can open the graph while the app runs. The buffer pool is capped at 256 MiB for the shared 4 GiB host.
- **Configuration:** `DATABASE_URL` (required) and `PODCAST_LADYBUG_PATH` (default `.local/ladybug/graph.lbug`). Local setup: [local_development.md](local_development.md).
- **Storage:** Compose runs `pgvector/pgvector:0.8.7-pg18-bookworm` on the private Compose network (no published port) and bind-mounts `/var/lib/podcast-analyst/postgres` and `/var/lib/podcast-analyst/ladybug` from the host. Data survives releases, container restarts, and Compose down/up, **but not EC2 instance replacement**; see [devops.md](devops.md#preserving-the-data-layer).
- **Ingestion additions (`002_ingestion.sql`):** `entities(id, name, kind, UNIQUE(kind, name))` and `claim_entities(claim_id, entity_id)` keep extracted entities in Postgres so the graph can be rebuilt from it; `episodes.claims_extracted_at` marks finished claim extraction. See [etl_design.md](etl_design.md).
- **Read-only SQL:** `postgres_database_query` runs each query as the `NOLOGIN` SELECT-only role `podcast_reader` (`SET LOCAL ROLE` inside a `READ ONLY` transaction), one statement at a time, with a 10 s statement timeout and capped output. For now only the ingestion extraction thread receives it; chat threads get it with the research skill.
- **Not yet built:** `vector_search`, `graph_query`, and the chat-side database tools.

## End product example:
Our data layer is designed to support a system that will work roughly like so:

> User:
"Have there been any podcasts discussing evidence that AMZN cannot sustain its data center buildout?"

*vector_search finds a hypothetical passage* -
Passage #42
Semantic match

Episode: AI Infrastructure Outlook · 18:34–19:12
"We are seeing meaningful power availability constraints that could delay several hyperscale projects, including projects involving AWS."


The graph contains:
```
Passage #42
  ← EVIDENCED_BY — Claim #9
                      |
                      +— ABOUT → Amazon
                      |
                      +— CHALLENGES → Thesis #3
```


And Thesis #3 says:
"AMZN will sustain aggressive AWS infrastructure expansion through 2028."

Codex now has both the relevant passage and an explicit relationship to the investment thesis.

It can explain that the podcast provides evidence of a potential constraint on AWS expansion, while distinguishing a possible delay from proof that Amazon cannot sustain its overall buildout.

It includes the verbatim quotation, podcast episode link, and timestamp.
